# RFI response packages

## Saved draft review

Each saved response now shows how many requirement answers contain text against the current requirement version without recognized unfinished markers. “Review saved draft” exposes missing answers, placeholder text, changed wording, removed requirements and the same company/evidence/internal checklist used by export. Capture/admin users can jump directly to the overview or affected answer; readers can inspect the saved draft without write controls. A complete text preview uses the same document assembler and disclosure checks as PDF/Word.

Counts describe drafting progress only, never completeness of the notice, compliance, approval or submission readiness. TODO/TBD and explicit bracketed drafting prompts are recognized; ordinary bracketed citations such as [1] are not. Placeholder warnings also appear in the exported internal review checklist. Missing or oversized/unavailable sources fail visibly when opening review. Reviews use saved answers and the currently loaded workspace snapshot; downloads still reload and recheck sources. Editing shows live answer progress and reminds the user to save before relying on downloads. No new database permissions, approval state or model calls were introduced.

Validation: six response tests passed, including placeholder/current-version distinctions and PDF/Word rendering. The authenticated staging workflow verified the saved review, full preview, direct focus to overview and requirement answers, downloads and role denial. Synthetic staging records were cleaned up. Lint, type checking, production build and secret scanning passed.

## Automatic company and bid information

All RFI, RFP and RFQ exports now include a company-information section and bid-information section. The response workspace previews the same data and links to Company to fill gaps. Company identity uses the workspace legal name, operating name and website. Current, sourced, verified workspace-visible identity, registration, NAICS and service-territory facts populate automatically, including contacts, addresses, phone/email and public identifiers when recorded in those categories. Licenses, capabilities and certifications additionally require current applicable evidence-use approval for a requirement in the selected pursuit. Restricted and role-restricted fact types remain excluded from these shared documents.

Bid details include pursuit and opportunity names, buyer, solicitation number, saved notice summary, official deadline with time zone, notice URL and source reference. Requirements and their citations continue to populate per section. Missing contact/address/phone/email and bid fields appear in the internal review checklist. Unverified, expired, future-effective and future-verified records are omitted; they are not promoted to verified by document creation. Pricing, authorization and missing narrative are not inferred.

Values refresh at export, including for existing saved drafts. Automatic data is separate from editable narrative, so updates do not overwrite answers. New assistant outlines no longer duplicate company/buyer/solicitation values inside saved free text. Legacy and manually written narrative may still contain old facts and needs review. After rendering, the export reloads its scoped sources and compares the complete rendered document before releasing bytes, covering company records outside the decision-context token. Profiles at the 500-row loading limit fail closed rather than silently exporting incomplete profile data.

Validation: five response tests passed, covering all three document types, contact and identifier population, fresh values, omissions, source limits and real PDF/Word text. The PDF information page was visually inspected. The authenticated staging workflow passed the new automatic-information preview and actual exports alongside command creation/replay, stale-edit denial and viewer denial; fixture records were cleaned up. Company setup now provides dedicated address, phone and email prompts. No migration or credentials changed.

## Assistant document commands

The authenticated assistant now accepts explicit standalone commands such as “Create an RFP for this bid”, “Draft an RFI response” and “Prepare an RFQ for the selected pursuit”. The command works in either answer mode on an open pursuit. Outside a pursuit it links to Pursuits instead of guessing a bid. Public demo conversations cannot create company records.

This is a deterministic document action, not model-authored narrative: it saves a real response outline containing company name, buyer, solicitation, a type-specific completion checklist, and current requirement sections. Answers remain empty and are flagged as missing during export. These are contractor responses; buyer-issued solicitations, automatic narrative generation and structured quote calculations remain outside this release. The interface states these limits.

The existing capture/admin authorization, session RLS, mutation allowance, requirement-version and review-context checks apply. A creation UUID makes a retried command reuse the saved draft; a concurrent duplicate insert cannot overwrite it. No approval or submission is performed. The result links to the saved response card, with editing and PDF/Word downloads. RFI, RFP and RFQ types persist through editing and export. Legacy schema-1 drafts without a kind default to RFI. No database migration, provider call, new credential or purchase is required.

Validated with four response tests and eleven existing assistant stream tests, plus the isolated authenticated staging browser workflow: no-pursuit guidance, actual RFP creation, replay of the same server-action request without a duplicate, opening the saved editor, PDF/Word downloads and rejected viewer creation. The staging availability badge is mocked; persistence, authorization and exports use the real staging application/database. Synthetic records and account were removed afterward. Lint, type checking, production build and secret scanning passed.

The first response-document workflow is an authenticated RFI draft composer on each pursuit. Capture managers and organization administrators can name a package, write an overview and answer the pursuit's saved requirements. Drafts persist in the existing `proposal_sections` table under the `RFI response:` title prefix with schema-validated JSON and `draft` status. This uses the existing tenant RLS, composite pursuit foreign key, update timestamp trigger and audit trigger. No migration or new credential is required.

The save action checks the user's current role, parent pursuit, mutation allowance, requirement IDs and versions, review context, and saved package version. It never accepts a browser claim of approval. A context or version mismatch retains the entered text and requests reconciliation. Reopening a saved draft retains answers for still-present requirements and identifies changed context; removed requirements are not carried into the new edit. The source-review acknowledgement is a browser usability check, not an approval or permanent attestation. Free-text answers are shared with the workspace, and the composer explains that restricted company information should not be pasted into them.

PDF and editable DOCX exports use saved narrative only, plus freshly loaded source requirements and current evidence-use reviews. Auto-populated company evidence must be workspace-visible, verified with a verifier/date/source, within its effective dates, and approved as applicable for that exact requirement. Restricted, unavailable, expired or stale evidence is not copied even for an administrator. Users with read access can download the shared draft; loss of workspace access denies the request. Exports are checked again for membership, saved version and (when enabled) source review context before bytes are released. A race can still occur immediately after the final check, and downloaded files cannot be revoked.

Each export includes a branded cover, saved package ID/update time, generation time, narrative responses, requirement citations, evidence IDs/versions/reviewer attribution, and an internal unresolved-items checklist. All pages are labeled Draft and not approved for submission. Bid/no-bid decisions do not approve a response document. The internal checklist is intentionally included: this first export is a working review package, not a buyer-ready final document. Regenerating a draft can change its evidence and warnings as records change; there is no immutable export archive or whole-document approval history yet.

Exports require an authenticated session and organization-scoped saved package. Responses are attachments with private/no-store caching. Export requests share the existing 20-attempt-per-minute user mutation allowance. Limits: 20 displayed recent packages (21 loaded to disclose truncation), 100 requirements per composer, 4,000 characters per answer, 6,000-character overview, 100,000-character saved payload, 180,000 characters in the assembled export and 160 PDF pages. Partial requirements/evidence views are rejected for export rather than silently presented as complete. A registered source can itself be incomplete; warnings do not certify notice coverage.

PDFs embed Noto Sans under the included SIL Open Font License. Unsupported glyphs produce an explicit error directing the user to DOCX instead of silently dropping text. DOCX files are editable and preserve Unicode; invalid XML control characters are rejected. Assets are bundled through the Next.js route tracing configuration. Rendering uses [pdf-lib](https://pdf-lib.js.org/) and [docx](https://docx.js.org/api/classes/Packer.html); PDF.js is used only for development validation.

Implemented: RFI response drafts, source population, evidence attribution, saved editing, PDF and Word export. Not implemented: issuing buyer RFIs, structured RFQ pricing, full RFP proposal templates, AI narrative generation, immutable export versions, document approval/signatures, procurement-portal submission, and uploaded PDF extraction. Those remain subsequent increments; no scanner or paid hosting was purchased.

Validation: the unit/integration tests generate real PDF/DOCX artifacts, parse their contents, verify draft footers on every PDF page, check text stays inside page bounds, preserve long answers and Unicode, and reject unsupported glyphs and XML control characters. Evidence tests cover restricted and expired facts, role-restricted fact types even when marked workspace-visible, stale approvals, changed requirements, malformed JSON, duplicate answers and partial-source limits. The PDF cover and response page were visually inspected. The isolated local app against hosted staging passed actual saved-draft reload and PDF/Word browser downloads, anonymous/foreign-tenant denial, stale exports and edits, revoked capture permissions, viewer write denial and mobile containment. Synthetic records and the temporary account were removed, and the fixture organization was suspended again. Lint, type checking, production build, deployment asset tracing and secret scan passed. Browser validation also found and fixed duplicate pursuit component keys that could disrupt editor state during refreshes.

# Company information requests

The Company completion checklist can now turn missing information into a named request with a due date. This extends the existing onboarding checklist rather than creating a second task system. Requests appear in Company and in a compact Today queue, with assigned-to-me, open, ready-for-review and closed filters. Due dates use the company's saved time zone.

An organization administrator creates or assigns a request. Its active, non-viewer assignee may update the progress note and mark it ready for administrator review. Only an administrator may close, reopen, rename or reassign it. Closing is an administrative checklist action: it does not write company facts, attest evidence, approve proposal use or change the profile-completion percentage. Requests and notes are visible to company members; private evidence belongs in the appropriately authorized Company record. No email or SMS is sent.

Migration `20260922003000_company_information_requests.sql` adds optional assignment, due date, Passport-item link and actor/completion attribution fields to `onboarding_items`. Existing checklist rows are retained without inventing owners or deadlines. Tenant membership foreign keys, one-request-per-Passport-item uniqueness, open-request indexes and monotonic update versions support safe edits. The checked, rate-limited RPC replaces direct authenticated mutations. Existing tenant read policies and before/after audit events remain. An administrator-only RPC lists active non-viewer company members for assignment; it cannot list another company's members.

Main application files: `lib/information-requests.ts` (validation and queue ordering), `app/information-request-actions.ts` (server action), `components/information-requests.tsx` (assignment and review), `components/profile-completion.tsx` (missing-item entry point), `components/tenant-workspace.tsx` (Company and Today), and the tenant types/loader. The shared capture form now supports native date inputs. No new package or external service is needed.

Release order: apply the additive migration before the application using `scripts/information-request-release.mjs staging|production apply-approved`. The release checks migration history/checksums, preserves existing row values and checks public-table RLS. Reverting the app does not require deleting the new data; keep the checked RPC and audit history. Do not restore direct mutation privileges as an application rollback.

Validation covers administrator/assignee/viewer boundaries, suspended/foreign owners, tenant reads, direct-write bypasses, duplicate requests, stale versions, progress/closure attribution, reopening, audit snapshots and unchanged profile facts. Hosted tests use synthetic accounts only. The SQL suite rolls back; browser fixtures are suspended and their accounts disabled afterward.

Limitations: requests are company-visible, in-app only and bounded to the existing 500-item workspace sample. The queue warns at that bound. Completing a request requires a separate human review of the saved evidence. Closed requests are reopened rather than duplicated for the same Passport item. This release does not modify the PDF guide or add request actions to the AI assistant.
